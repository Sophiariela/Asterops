From studio to platform.

An audit of Sophiariela/Asterops, an architecture for Aster Core, a CommerceOS MVP, and the smallest version that can actually be sold. No code has been changed.

Verdict — reuse

The marketing layer is in good shape and content-driven. Keep it. Roughly 70% of Phase 1 already exists.

Verdict — gap

There is no product layer at all: no auth, no database, no tenancy, no billing. Notion is the only place data persists.

Verdict — blocker

The repo sells three products. This brief sells five. That contradiction has to be resolved before anything is built — see Decisions.

03 · Data model

Fourteen entities. Organization is the tenant.

Every row that isn't platform catalog carries an organization_id. Tenancy is enforced at the database, not in application code.

Notion during the transition

Notion stays the CRM through Phase 2 — it is where the team already works, and Lead is the only entity it holds. Aster Core writes leads to Postgres and mirrors them to Notion via the existing createLeadInNotion() path, so nothing the team relies on breaks. The mirror is deleted when admin lead management ships in Phase 3 — not before, and it is one function to remove.

07 · Smallest sellable version

Sell the system before automating the fulfilment.

The eight-step builder is the wrong first build. It is months of configuration, provisioning and billing infrastructure before a single customer proves they will buy a system instead of a project. There is a version that takes weeks and produces real revenue.

Recommended MVP Concierge-provisioned self-serve

Diagnostic → recommendation → paid configuration → Aster provisions by hand.

What it proves
{{ pv }}

The customer experience is already self-serve: they diagnose, they see a price, they pay online, they get a system. Only the provisioning is manual — and that is invisible to them. Automate it in Phase 3, once there is repeat volume proving which configuration choices customers actually make. Building the builder first means guessing those choices.

Also noted — Aster Labs

Labs fits Phase 1 as a content-driven route, reusing the existing config-plus-types pattern with a LabEntry type on the Problem / Observation / Friction / Opportunity / Recommendation structure. One hard constraint in the type itself: entries carry a required relationship field whose only value for third-party subjects is "independent-analysis", rendered as a visible label on the page.
